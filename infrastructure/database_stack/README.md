# LSMP Database Stack

This directory contains the infrastructure configuration, schema definition, and utility control scripts for the PostgreSQL and TimescaleDB database layer of the LSMP project.

---

## 📂 Directory Structure

```text
infrastructure/database_stack/
├── docker-compose.yml     # Docker Compose service definition
├── .env.example           # Environment variables template
├── schema.sql             # SQL script for database initialization
├── test_schema.sql        # SQL script for schema/constraint testing
└── scripts/               # Management control scripts
    ├── run.sh             # Startup & recovery script
    ├── stop.sh            # Service shutdown script
    └── test.sh            # Automated verification test runner
```

---

## 🏛 Database Schema Architecture

The database consists of **5 main tables** optimized for high-volume time-series security events and anomaly analysis.

### 1. Hypertables (TimescaleDB Optimized)

*   **`log_event`**
    *   **Description**: Stores raw, unstructured security alert logs forwarded from Wazuh Manager.
    *   **TimescaleDB Config**: Partitioned by day (`timestamp`).
    *   **Policies**:
        *   **Compression**: Active after 7 days (grouped/segmented by `event_type` and `source_ip` for optimal space saving).
        *   **Retention**: Auto-purged after 90 days.
*   **`anomaly_result`**
    *   **Description**: Stores processed feature windows and inference scores generated by AI detection models.
    *   **TimescaleDB Config**: Partitioned by week (`window_start`).
    *   **Policies**:
        *   **Compression**: Active after 30 days.
        *   **Retention**: **None** (saved indefinitely to support future AI retraining).

### 2. Regular Tables (Standard PostgreSQL)

*   **`risk_score`**
    *   **Description**: Holds the final aggregated risk priority score displayed on the analyst dashboard.
    *   **Relationship**: Enforces a strict `1-to-1` relation with `anomaly_result` via a `UNIQUE (anomaly_result_id)` constraint.
*   **`attack_scenarios`**
    *   **Description**: Stores cataloged, time-bounded attack scenario metadata executed during simulation runs (used for automated ground-truth labeling).
*   **`evaluation_metrics`**
    *   **Description**: Logs benchmark scores (Precision, Recall, F1, Latency, Throughput, CPU/RAM resource usage) across different detection pipeline configurations.

## 🚀 Getting Started

### 1. Prerequisites
Ensure you have Docker and Docker Compose (v2+) installed on your machine.

### 2. Configuration
Copy the environment variables template and configure your credentials if necessary:
```bash
cp .env.example .env
```

### 3. Startup & Operations
All commands should be executed using the control scripts located in the `scripts/` directory.

> **Important**: Ensure scripts have execution permissions before running them:
> ```bash
> chmod +x scripts/*.sh
> ```

#### A. Start the Database Stack
To launch the database container normally (retaining existing data):
```bash
./scripts/run.sh
```
*If starting for the first time or if tables are missing, the script will automatically initialize the database schema from `schema.sql` once the container becomes healthy.*

#### B. Clean & Reinitialize (Fresh Start)
To discard all local data, perform backup, and start with a fresh schema:
```bash
./scripts/run.sh clear
```
*This will:*
1.  Verify if the container is running and generate a **logical schema/data backup** (`.sql.gz`) as well as a **physical archive** of the database volume (`.tar.gz`) under the `backups/` directory.
2.  Destroy existing database container and local state volumes.
3.  Launch a clean container instance and run the schema setup.

#### C. Stop the Stack
To safely stop the database service without losing data:
```bash
./scripts/stop.sh
```

To stop the containers and wipe Docker-managed container configurations:
```bash
./scripts/stop.sh remove
```

#### D. Verify & Test Schema Constraints
To validate schema structure, boundary limits, `CHECK` expressions, and logic validation queries:
```bash
./scripts/test.sh
```
*This executes a sandbox transaction verification loop utilizing Postgres `SAVEPOINT`s to verify that invalid configurations are rejected and correct relationships function properly.*
